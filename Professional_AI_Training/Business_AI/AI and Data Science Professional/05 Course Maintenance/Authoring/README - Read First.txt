AUTHORING SOURCES: HOW THE COURSE IS BUILT

Everything students and the tutor see is generated from files in this folder. Edit a source, rebuild, check.

Sources
  Build/curriculum.py             the 24 sessions: titles, questions, outcomes, topics, tools, licences, benchmark mapping
  Content/sNN.json                the content of session NN: vocabulary, slides, speaker notes, lab cells (exemplar: s07.json)
  Build/build_teaching_data.py    generates every dataset and answer_key.json from a seed (numpy and pandas only)
  Build/figs.py                   draws the 60 explanatory figures and 6 title images from the data
  Build/deckkit.py                the slide engine: 16 slide types, measured text fitting, native animations
  AUTHOR BRIEF.md                 the instructions the session authors followed (rules for slides, notes and labs)
  REVIEW BRIEF.md                 the instructions for the review pass over finished sessions
  Build/make_docs.js              the seven Word documents: Student Setup Guide, Sheets Lab Sheets, Sheets Lab Answers, Glossary, Assessment and Capstone Guide, Course Plan and Tutor Guide, Benchmark and Design Report

Commands (run from the Build folder)
  python3 build_course.py data         regenerate data, figures, lakeside.db, lakeside_for_sheets.xlsx and data.zip
  python3 build_course.py check N      build session N in memory and run every check
  python3 build_course.py build N      write the deck and the two notebooks (build all for every session)
  python3 check_course.py              course-level checks (duplicate vocabulary, figure names, titles)
  python3 export_docs_data.py && node make_docs.js    rebuild the seven Word documents
  python3 make_roadmap.py              rebuild the one-page roadmap (pptx and pdf)
  python3 make_playback_checklist.py   rebuild the checklist
  Wording in a Word document, the roadmap or the checklist is fixed in its generator (make_docs.js, curriculum.py, make_roadmap.py, make_playback_checklist.py) or in the Content file, never in the generated file.

Design system (deckkit.py, figs.py, make_docs.js, make_roadmap.py share it)
  ink 1F2328, body 3B4046, soft 6A6F75, hairline C9C5BC, accent B04A2B (clay), moss 5E7A57 for good outcomes in charts; Cambria headings, Calibri text, Courier New code.
  Type and hairlines, almost no fill (the only light fill is the grey well behind code output). No cards, numbered circles, kicker labels, banner bars or tile rows. Change the colours in one place per file.

What `check` does
  fits every slide (text that cannot fit at its minimum size is an error); lints every speaker note (no stage directions, one paragraph per click, no banned phrasing);
  executes every pandas, numpy, matplotlib, seaborn and SQL block on a slide or in a lab solution against the real data and compares the slide's printed output with the real output;
  checks structure (recall slide first, a trap, a lab, an exit check, a summary, at least five animated slides, vocabulary count).
  Code that needs scikit-learn, SciPy, statsmodels, PyTorch, Transformers, sentence-transformers or Streamlit can only be syntax-checked on a machine without them. On a machine that has them, `check` executes those blocks too.

If you change the data generator, the numbers in the slides and labs can go stale. `check` finds them (a slide output that no longer matches the real output is an error), and the content file must then be updated. Session 21 was reworked this way after the feedback data was regenerated.
